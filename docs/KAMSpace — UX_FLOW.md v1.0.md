# 1. Назначение документа

`PRODUCT.md` определяет, **что представляет собой KAMSpace и какие задачи он решает**.

`UX_FLOW.md` определяет, **как пользователь взаимодействует с приложением**:

- откуда попадает на экран;
- что видит;
- что может сделать;
- куда приводит каждое действие;
- как связаны между собой разные модули;
- какие состояния интерфейса необходимо предусмотреть.

Документ не определяет финальные:

- цвета;
- шрифты;
- размеры;
- графический стиль;
- анимации;
- визуальную айдентику.

Это будет зафиксировано позже в `UI.md`.

---

# 2. Основной UX-принцип

KAMSpace должен экономить время пользователя, а не создавать новую обязанность по ведению KAMSpace.

Поэтому приоритеты интерфейса:

1. минимум действий;
2. минимум обязательных полей;
3. никакого ручного дублирования информации;
4. часто используемые действия доступны быстро;
5. редко используемые функции не занимают главный интерфейс;
6. информация показывается там, где она полезна, даже если редактируется в другом разделе.

Пример:

Меню редактируется через:

`Ещё → Меню`

Но сегодняшнее меню отображается сразу на:

`Сегодня`

---

# 3. Платформа

Основной интерфейс проектируется по принципу `mobile-first`.

Приоритет:

1. iPhone;
2. Android;
3. desktop — после стабилизации мобильной версии.

Базовая ширина wireframe в Figma:

`390 px`

Интерфейс не должен зависеть от конкретной модели телефона.

---

# 4. Нижняя навигация

Постоянная нижняя панель содержит четыре раздела:

`Сегодня | Задачи | Календарь | Ещё`

Это единственная постоянная глобальная навигация мобильной версии.

Состав панели может быть пересмотрен после периода реального использования приложения.

# 6. Общие правила взаимодействия

## 6.1. Простые действия

Простые объекты создаются преимущественно через `bottom sheet`.

Примеры:

- задача;
- событие;
- покупка;
- человек;
- важная дата.

Не создавать отдельный полноэкранный маршрут, если действие занимает несколько полей.

---

## 6.2. Быстрое выполнение

Действия вроде:

- выполнить задачу;
- купить товар;
- добавить блюдо в меню;

не требуют дополнительного подтверждения.

---

## 6.3. Undo

После действий, которые пользователь может совершить случайно, желательно показывать краткую возможность:

`Отменить`

Например после выполнения задачи.

---

## 6.4. Удаление

Удаление объекта:

`Удалить`

↓

подтверждение

↓

`Корзина`

Объект не уничтожается сразу.

---

## 6.5. Единый источник данных

Календарь не создаёт копии объектов.

Например:

`Задача → deadline → отображается в календаре`

При нажатии открывается сама задача.

То же правило действует для:

- дней рождения;
- меню;
- покупок;
- важных дат.

# 10. TODAY-01 — Основной экран

Основная информационная иерархия:

### Верхняя область

- текущая дата;
- профиль/аватар;
- компактная карточка `Завтра`.

### Фото дня

Небольшая эмоциональная карточка.

### Сегодня

Общий список:

- задач;
- событий;
- напоминаний.

### Сегодня едим

Компактное отображение меню дня.

### Покупки

Краткая информация о покупках на сегодня.

### Ближайшее

- дни рождения;
- значимые даты;
- другие ближайшие события.

### Мы

Небольшая эмоциональная/статистическая карточка.

# 35. Одинаковые ингредиенты

В MVP автоматическое объединение одинаковых ингредиентов не выполняется.

Например:

`Лук — 1 шт`

и

`Лук — 2 шт`

могут существовать как две строки.

Автоматическое суммирование откладывается.

# 57. Основной дневной сценарий

В течение дня пользователь:

- закрывает задачи;
- отмечает покупки;
- получает полезные push;
- добавляет задачи;
- добавляет события;
- открывает календарь.

Большинство действий должны выполняться без глубокого погружения в структуру приложения.

# 62. UX состояния

Каждый основной экран должен иметь минимум следующие состояния:

## Normal

Есть данные.

## Empty

Данных ещё нет.

Вместо пустого белого пространства:

- короткое объяснение;
- понятное действие.

Пример:

> На сегодня задач нет.

`+ Добавить задачу`

## Loading

Не блокировать интерфейс больше необходимого.

## Error

Сообщить о проблеме понятным языком.

Не терять уже введённые пользователем данные формы.

---

# 63. Формы

Если пользователь начал вводить объект и произошла ошибка сети:

введённые данные не должны исчезать.

Обязательное поле не заполнено:

↓

основная кнопка недоступна либо рядом показывается конкретная ошибка.

Не использовать длинные формы без необходимости.

---

# 64. Чего не должно быть в интерфейсе

Не создавать:

- перегруженные dashboard;
- десятки категорий;
- множество статусов;
- внутренний чат;
- геймификацию;
- сложную систему баллов;
- отдельный экран для каждого мелкого действия;
- обязательное описание там, где достаточно названия;
- подтверждение очевидных безопасных действий;
- скрытое автоматическое изменение данных.

---

# 65. Приоритет информации

В конфликтной ситуации действует правило:

**Сначала действие → потом информация → потом декор.**

Пример:

Карточка задачи прежде всего должна позволять понять:

- что сделать;
- когда;
- кому;
- выполнено ли.

Только после этого можно добавлять декоративные элементы.

# 68. Критерий успешного UX

Пользователь не должен думать:

> В какой раздел мне сейчас нужно идти?

Основные повседневные сценарии должны становиться очевидными после нескольких дней использования.

KAMSpace должен ощущаться не как система учёта совместной жизни, а как удобный слой поверх неё.
